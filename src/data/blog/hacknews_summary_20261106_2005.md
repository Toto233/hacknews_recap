## 1. Claude Code 被曝外发用户邮箱，修复仍在进行 (Claude Code sends your email address to websites)


Claude Code 用户在 GitHub 报告，助手访问第三方网站时，未经询问便把邮箱写进 User-Agent，也就是用于说明请求来源的网络请求头。报告者使用 macOS 上的 2.1.318 版，并将近期诈骗邮件增多归因于此，但帖子没有证明这些邮件的来源。后续用户称，邮箱既可能来自账号信息，也可能来自 Git 配置；有人查到助手自行生成的联网命令包含邮箱。项目贡献者表示，2.1.317 起默认启用隐私检查。不过另有用户报告，启用检查后仍有漏拦情况。Claude Code 开发者随后解释，团队曾为减少作者署名等任务中的编造，把账号邮箱加入模型上下文，模型有时便用它满足网站索取联系方式的要求。团队计划在下周初的版本中移除这项账号信息；现有检查仍不能覆盖助手自行编写并运行脚本等路径。这是尚在修复中的信息外发问题，不能视为已经全面解决。

原文链接：https://github.com/anthropics/claude-code/issues/107757

论坛讨论链接：https://news.ycombinator.com/item?id=50385272

HN 的争论集中在：网站要求自动客户端提供联系方式，是否足以授权助手发送用户邮箱。varenc 起初用 SEC 接口解释这一行为，随后修正测试结论，称多数非默认 curl 请求标识也能通过，并非必须提供邮箱。T-R 表示自己已有专用工作邮箱，助手却擅自发送私人地址；另一位评论者认为即便有联系政策，也应先询问用户选择哪个地址。有人将此视为模型难以可靠遵守隐私意图的问题，也有人强调，约束联网命令应由外围软件强制执行。还有评论指出，移除账号邮箱后，助手仍可能从 Git 历史读到地址。

## 4. 一个星号串起十年漏洞：部分 musl 系统的 SSH 密码验证可被绕过 (sshole)





本应只准密钥登录的账户，可能因密码字段里的一个星号被错误放行。研究者 Özgün Kültekin 披露了名为 sshole 的漏洞：部分采用 musl C 运行库、未启用 PAM 身份验证模块的 Linux 系统受影响，OpenSSH 已在 10.6p2 加入修复。问题来自几个旧设计的叠加：账户用星号表示不接受密码；musl 的密码散列函数出错时也可能返回星号；OpenSSH 为避免通过响应时间探测账户，计算时可能借用另一账户的散列参数，最后却拿结果与原账户字段比较。错误标记因此可能被当成验证成功。触发还要求启用密码登录，并存在可供借用的真实密码散列，不能据此认定所有 Alpine 或容器都受影响。作者回溯了这些设计如何从不同年份的兼容性与安全补丁中形成，并建议更新 OpenSSH；暂时无法更新时，可关闭密码登录。使用 glibc 或通过 PAM 验证的配置不属于文中这一漏洞范围。

原文链接：https://sshhole.com

论坛讨论链接：https://news.ycombinator.com/item?id=50378228

HN 的主要争论是：谁该保证错误结果绝不等于有效密码字段？评论者拆解出，musl 原本会根据传入的散列参数选择错误标记，但 OpenSSH 借用了另一账户的参数，破坏了这个防误匹配假设。有人因此主张为 crypt() 加统一包装，明确区分成功值与错误；也有人把问题归于类型设计，认为返回普通字符串容易把失败当成数据。回复则指出，空指针本来就能表示无结果，关键仍是调用方是否检查，以及接口有没有清楚表达失败。讨论没有把换语言视为已获证明的万能修复。

## 5. Alpine 修补 OpenSSH 密码认证绕过漏洞，升级后还须重启服务 (Alpine Linux Security Advisory: OpenSSH-server password authentication bypass)


Alpine Linux 发布安全公告：部分启用密码登录的 SSH 服务器，可能让攻击者在不知道密码的情况下进入账号。漏洞需要多个条件同时成立：服务器使用 musl，未通过 PAM 认证；目标账号的密码字段为星号，且系统另有账号使用特定类型的密码哈希。星号通常用于没有设置密码、只打算使用密钥登录的账号。问题出在底层密码计算失败时也返回星号，服务器把错误结果与账号字段比较，误判为认证成功。公告确认 Alpine 3.16 至 3.24 及 edge 中存在受影响配置，并已为这些分支提供更新；仅安装软件包还不够，必须重启 sshd 才会替换运行中的服务。无法立刻升级时，可关闭密码认证并重启，操作前应先确认密钥登录有效。默认禁止 root 密码登录能保护 root，但不能保护可再提权的其他账号。未运行 SSH 服务的容器、已关闭密码认证或启用 PAM 的系统不受此问题影响。

原文链接：https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/

论坛讨论链接：https://news.ycombinator.com/item?id=50379704

这条提交的评论已由 HN 管理员合并至较早的主讨论串。主串先争论影响范围：有人认为多项条件须同时满足，不应解读为所有 OpenSSH 都能被绕过；另有人指出 Alpine 的常见账号及认证配置就可能满足这些条件。关于关闭密码登录，有人主张改用密钥，也有运维人员举出银行、保险客户坚持用密码传输文件的实际限制。技术讨论则追问错误为何被当作有效密码结果：一方批评底层库的错误返回设计，另一方指出 OpenSSH 为隐藏账号状态而借用别人的哈希参数，也参与造成了问题。主讨论：https://news.ycombinator.com/item?id=50377221

## 6. 微软画图出现高危远程代码执行漏洞，官方标记无需用户交互 (MS Paint Remote Code Execution Vulnerability)


微软画图的 CVE-2026-83844 漏洞记录指出，一处越界读取错误可能让未获授权的攻击者通过网络执行代码。越界读取是程序读取了允许范围之外的数据；这份记录将后果列为代码执行，而不只是信息泄露。微软给出的 CVSS 基础评分为 8.1，属于高危；评分同时标明攻击复杂度高、无需权限、无需用户交互，成功后可能严重影响数据保密性、完整性和系统可用性。受影响范围列为 Microsoft Paint 11.0.0.0 起、低于 11.2605.91.0 的版本，并附有微软官方修复公告。记录于十月十三日公布，十月三十一日更新，因此并非今天才披露的新漏洞。公开条目没有说明画图究竟通过哪个网络入口触发问题，也未把问题归因于 AI 功能。记录中的漏洞利用成熟度仍为未经证实，CISA 的十月评估亦标注未发现利用；这些是相应记录时点的状态，不能据此保证当前没有攻击。

原文链接：https://www.cve.org/CVERecord?id=CVE-2026-83844

论坛讨论链接：https://news.ycombinator.com/item?id=50384233

HN 最关心的是，画图为何会有无需交互的网络攻击入口。有人猜测与 AI 功能、图片文件或系统服务有关，但未给出证据；jdiff 多次指出，要求用户点击并打开恶意图片的解释，与官方“无需用户交互”描述不符。另有人怀疑微软公告使用了通用模板，认为仍须等技术说明，不能仅凭标题推导攻击过程。更新方式也引来抱怨：用户称 Windows Update 没有提示，打开 Microsoft Store 才取得新版画图。也有人对各处修复版本表述提出疑问，因此讨论中的版本号不能直接当作已验证的修复依据。

## 7. MCP Explained：用交互消息流讲清 AI 如何调用工具 (MCP Explained)



Runlayer 制作了交互教程 MCP Explained，用逐步播放的消息流解释模型上下文协议：它为 AI 应用连接工具和数据规定统一接口。教程先区分用户、模型、宿主应用和服务器：服务器公布工具清单，应用把说明交给模型，模型提出调用，应用实际执行后再把结果传回，模型并不直接连服务器。读者可切换工具、资源、提示词、授权和传输等课程，同时查看参与方、消息顺序和实际 JSON 内容。页面还提供规范版本切换，以及工具描述投毒、返回内容中的提示注入、钓鱼等攻击演示，说明权限和可信边界为何仍须由应用落实。网站特别区分协议与上层实现：工具搜索和代码批量调用属于宿主的组织方式，并非 MCP 新增的消息类型。基础课程以 2025 年 11 月规范为底，并标出后续版本和扩展的变化，因此阅读握手、双向请求等细节时，要留意所选版本。

原文链接：https://mcp-explained.com/

论坛讨论链接：https://news.ycombinator.com/item?id=50379249

讨论最集中的是：动画是否真能帮助初学者。多位读者认为，多个面板同时更换文字和消息，容易让已懂协议的人觉得直观，却让新人找不到学习顺序；他们希望先看一个具体任务、少量图示，再进入参考资料。也有人指出，网页已明确写出 MCP 不是 REST，不能用这个类比纠正教程。关于实际价值，一派认为命令行更易组合和处理大量结果；另一派举企业 OAuth 授权、只读数据接口和非开发者查询科研数据为例，认为统一接入能减少凭据管理和领域查询的负担。

## 8. 被收集了这么多数据，为什么科技公司仍不懂我的需求？ (I wish tech companies knew more about me)





博主 Rakhim 用一连串亲身经历质疑个性化服务的实际效果：科技公司收集了大量行为数据，却常连明确、重复的偏好也用不好。他买完床垫、手柄后仍被推荐同类商品；多年跳过带人声的电子乐，播放列表依旧照推；明明账号、系统和浏览器都选英语，服务仍因所在国家切成芬兰语，旅行时又改成德语。一次查炉具安装说明，被算法当成了长期爱看炉具视频。更直接的问题出现在公司已有确定信息的场景：银行推销他早已购买的车险，航空公司提供与其护照国籍不符的签证提醒，只有一个用户的 Netflix 账号却每次都要求选人。文章并不否认数据被追踪、储存和出售，而是反问：既然这些信息已经存在，为何不能用来减少重复操作、识别一次性需求、尊重明示设置？这些是个人体验列举，未证明平台掌握了所有相关数据，也未测量推荐系统的整体准确率。

原文链接：https://rakhim.exotext.com/i-wish-tech-companies-knew-more-about-me

论坛讨论链接：https://news.ycombinator.com/item?id=50378942

评论把“不了解用户”和“不以用户利益为目标”区分开来。有人认为广告商要卖的是自己的商品，平台优化的是转化与收益；跨站追踪也可用于低价触达高价值网站的访客，未必为了理解真实需求。另一些人提醒，好推荐容易被当成理所当然，坏推荐更显眼，单凭体验可能存在选择偏差。还有评论指出，语言设置和单用户选择页根本不需要更多追踪，尊重用户已明确表达的选项就能修好。音乐爱好者则怀念 Last.fm 和 Pandora 的推荐，并讨论显式反馈为何比被动收集更有用。

## 9. 收藏夹不是档案：一位博主如何保存最爱的 YouTube 视频 (Download your favourite YouTube videos)





为了在电视上随时播放陪自己入睡的游戏实况，一位博主把数百条 YouTube 视频搬进了家中的媒体库。他在文章中主张，喜欢的内容可能从平台消失，值得主动归档；随后展示了自己的复杂方案。普通需求用 yt-dlp 或其界面工具，加一个硬盘或网络存储文件夹就够，他则需要自动维护几十个播放列表。媒体服务器 Jellyfin 习惯按电视剧的季与集组织内容，难以直接表达这些列表；他用 ytdl-sub 管理下载与元数据，把播放列表名称映射到季字段，避免同一视频同时出现在年份和列表两套分类里。为缓解容量压力，他还用 Tdarr 转成 HEVC/H.265，称自己的 2TB 媒体库节省了约 700GB。但这套工具界面复杂，复杂流程容易出错，转码后还可能丢失缩略图；已导入视频的分类也不易修改。文章是一份个人家庭媒体库经验，作者明确认为整套配置对多数人过于繁重。

原文链接：https://criminallyvulgar.dev/you-should-absolutely-download-your-favourite-youtube-videos/

论坛讨论链接：https://news.ycombinator.com/item?id=50378571

HN 的讨论围绕“保存哪些、保存到什么程度”展开。有读者称五年前的播放列表约有一成内容已不可用，另有人建议保留视频编号，借搜索结果或 Internet Archive 寻找线索。支持归档的人强调，收藏链接不能保证未来仍能观看；容量派则提醒，囤积可能消耗大量硬盘、时间和维护精力。有评论建议给访谈、解说等内容选择较低清晰度，只保存自己真正看过或重视的视频；另有人补充，家庭流量上限也会拖慢批量保存。这些比例与成本估算均来自个人经验，不能当成平台整体统计。

## 10. Salon 宣布停止出版，31 年网络新闻探索落幕 (Goodbye from Salon)


创办于 1995 年 11 月的网络媒体 Salon，于 2026 年 11 月 5 日发表告别声明，宣布在运行 31 年后停止出版。声明给出的直接解释是，独立数字新闻的商业现实已经深刻改变，经过考虑，团队认为现有出版模式无法继续维持。它没有进一步列出财务数字，也没有把决定归因于某一家平台或某项技术。Salon 回顾，创办时互联网仍是新领域，一小群记者希望以鲜明的声音、好奇心和新的读者关系，探索网络新闻可以怎样运作。此后网站把政治、文化、评论与思想放在一起，既报道新闻，也尝试解释变化，为较少受到关注的视角留下空间。告别信感谢历任记者、编辑、摄影师、制作与设计人员、商业团队、撰稿人及读者，强调阅读、订阅、分享和争论共同形成了社区。对这家早期网络出版物而言，声明把过去的报道与读者关系视为最重要的遗产，而没有公布下一步重启或转型安排。

原文链接：https://www.salon.com/2026/11/05/goodbye-from-salon/

论坛讨论链接：https://news.ycombinator.com/item?id=50383739

HN 的争论从 Salon 延伸到原创报道还能由谁付费。一条热门评论称新闻编辑部岗位减少约六成，回复随即纠正口径：皮尤研究显示，2008 至 2020 年美国报纸编辑部岗位下降 57%，涵盖数字媒体、广播电视等领域的总降幅是 26%，两者不能混用。另一路讨论认为，网上专家和当事人的直接叙述扩大了信息来源，削弱了传统媒体的独占地位；反方则强调，信息越多，核实、筛选与专业采访越有价值。有人担忧编辑支持减少，但这些行业观察不能直接证明 Salon 停刊的具体原因。
