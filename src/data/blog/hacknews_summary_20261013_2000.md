## 1. 网站如何用浏览器指纹追踪你：清 Cookie 为什么不够 (Fingerprints are the new cookies)



Roy Fish 用一个网页演示浏览器指纹：页面测量设备特征，把结果转成固定昵称，让读者尝试刷新、清除 Cookie 或连接 VPN，观察身份标记是否变化。它不依赖网站保存的小文件，而是组合浏览器主动暴露的信息。网络请求会带出语言、系统和 IP；网页脚本还能读取显卡特征、处理器线程数、字体，以及绘图和音频计算产生的细微差别，通常无需另行请求权限。

单项特征可能属于数百万人，组合后却能缩小候选范围。作者用猜人物游戏解释这种识别能力，也提醒特征之间可能相关，不能简单累加信息量。演示只是把几项测量值合成哈希，任一值改变就会换昵称；作者称商业追踪系统还会处理部分特征变化。文章介绍两条防护思路：给测量结果加入扰动，或让用户呈现相同特征。关闭 JavaScript 能阻止本页演示，却仍会暴露网络信息；隐私扩展也可能因配置少见而增加可辨识性。

原文链接：https://royfish.dev/fingerprints-are-the-new-cookies

论坛讨论链接：https://news.ycombinator.com/item?id=50048642

抽样讨论追问：新闻网站为什么能在未征询同意时处理音频、读取离屏绘图结果？首位评论者希望把这些能区分设备的接口纳入权限管理。他接受主动提供地区、年龄段和兴趣的广告定位，但反对追踪私人交流。另一人把问题归因于浏览器厂商与广告业务的利益关联，这是评论者的解释。回复者引用旧式移动 Java 的权限弹窗经验，认为逐项打断操作难以改善体验。还有人指出，用户通常只想看新闻或照片，难以理解接口用途，网站可能借界面设计诱导许可；争论因此涉及同意是否足够知情。

## 2. Meta 发布 Muse Wonder，强调跨对话记忆与持续执行任务 (Muse Wonder)


Meta 于 10 月 12 日发布 Muse Wonder 和 Muse Wonder Full，面向能代用户完成个人及工作任务的 AI 代理。官方强调跨对话保留重要背景、按需找回信息，以及持续推进目标的能力：遇阻尝试其他办法，适应新信息，必要时澄清需求并在重要行动前确认。公司通过长期软件项目等评测检验持续执行，另测试法律、金融和健康任务。官方认为，更强的基础模型能让后续训练收益迁移到训练未重点覆盖的陌生任务；这是 Meta 自有评测的结论。Muse Wonder 已通过 Meta Model API 和 Muse Code 提供，Full 版本供 Muse Code 订阅者使用；Muse 产品内的体验将随后先向订阅者推出。由于代理会接触消息、日历和私人文档，Meta 也强调隐私处理与抵御恶意指令，并称更完整的安全评估报告将另行公布。

原文链接：https://research.meta.ai/blog/muse-wonder

论坛讨论链接：https://news.ycombinator.com/item?id=50059115

HN 评论从新模型转向前沿 AI 的竞争与自我改进。有评论者认为，多家公司接近前沿可避免权力集中，并希望参与者来自不同国家；另有人质疑模型递归改进自身是否必然发生。GodelNumbering 指出，确认下一版确实优于上一版很难，人类和旧模型都可能无法充分判断。还有评论者认为，更聪明的系统也可能更难提升，收益未必爆炸式增长。tibbar 提出可比较新模型达到旧能力所需的计算量，但承认不同领域验证难度不同。另一条回复担忧，可量化能力变强时，价值取向等难以验证的性质可能更难掌控。

## 3. GLM-Legal 发布：把法律推理接入完整工作流程 (GLM-Legal)


Z.ai 发布法律专用模型 GLM-Legal，重点是从分散文件中提取事实、组织论证，再交付符合任务要求的文档。它以 GLM-5.3-Flash 为基础，先用法律语料强化概念与规则，再在数万个模拟法律环境中进行强化学习。团队同时迭代模型和负责管理上下文、工具与反馈的运行框架，并把律师发现的漏项、引用和格式问题反馈到训练中。官方称，该模型在覆盖 24 个业务领域的 Harvey LAB 上取得 19.2% 的全项通过率，比基础模型高 12.5 个百分点；这表示任务须满足全部评分要求，不等于法律回答准确率。Harvey LAB 和 LegalBench 结果由 Vals 独立评测。文章还展示合同退出条款修改、40 份文件的证据分析和跨境隐私合规计划，准备接入桌面代理 AutoClaw；API 目前开放申请测试，演示文档仍交由专业团队审核。

原文链接：https://z.ai/blog/glm-legal

论坛讨论链接：https://news.ycombinator.com/item?id=50058507

已抓取的两条 HN 评论关注常规法律工作和新问题是否应分开评测。一位评论者分享，供应商合同通常沿用类似模板，他先用 Claude 完成几轮修改，再请律师终审，节省了费用；这支持模型承担初级工作，却不能证明它能处理合伙人面对的重要判断。另一位评论者把问题延伸到人才培养：合同审阅、编码等基础任务若被自动化，新人可能失去反复查找资料、辨别错误和积累细节经验的机会。他认为让新人借助模型工作很自然，但尚不清楚怎样保留这段学习过程。两人的经验与疑问并非 GLM-Legal 的实测结论。

## 4. Codex CLI 用户要求后台常驻服务改为主动开启 (Codex CLI installs a persistent, self-updating background daemon by default)


一名 Codex CLI 用户在 GitHub 请求把后台服务自动启动改为默认关闭，或先征询用户。报告针对 npm 安装的 0.157.0 版，环境是 Linux／WSL2。按他的观察，打开交互会话会启动守护进程，关闭所有窗口后仍继续运行；程序还把约 374 MB 的软件包复制到独立目录，由另一个后台进程定时检查更新。包管理器安装的版本与实际处理请求的后台版本因此可能分离。

报告者还称，服务沿用首次启动会话的环境变量，后来修改代理设置不会改变已有服务的连接；停止服务的命令也没有终止更新进程。他认为常驻模式适合桌面应用或远程控制，但命令行工具应更清楚地交代生命周期和更新方式，并提出在最后一个客户端断开后退出等方案。Windows 用户也报告类似问题，有人称在 0.160.0 环境未见守护进程。这是一项带有具体版本和环境的用户报告及功能请求，不能据此断言所有版本、安装方式均有相同表现。

原文链接：https://github.com/openai/codex/issues/48195

论坛讨论链接：https://news.ycombinator.com/item?id=50060694

HN 抽样评论关注后台服务的用途与默认开启是否匹配。有人指出仍有 daemon_auto_start 开关可关闭自动启动，但批评设置缺少文档。另一人承认服务对自定义应用工具有用，也主张默认关闭。其他人更在意升级后出现持续运行、关闭客户端也不退出的进程；有用户说服务无法启动，才发现多了这一组件。讨论还涉及旧版本副本占用磁盘：一人报告自己机器约占十二 GB，属于个人观测。回复有人建议定时清理，也有人认为让模型删除文件过于复杂，另有评论者倾向采用可丢弃的虚拟机环境。

## 5. 用 C 和 CGI 做商业网站：一个二进制文件背后的取舍 (A Modern Web App in C)


Corey Prophitt 用 C 和 CGI 做出商业网站，支持账号、内容创作者搜索、文件夹管理、支付和邮件通知，页面无需浏览器脚本。CGI 是网页服务器调用应用的接口：每次请求启动进程，读取请求后直接输出页面。他采用 OpenBSD、httpd 和 SQLite，把静态资源也编进可执行文件；更新时替换这个文件，后续请求便运行新版。

作者看重系统容易理解和维护：没有框架、模板语言、容器或独立数据库服务，程序能直接在命令行调试。对外请求、密码处理和 JSON 解析交给少量库，数据库与 JSON 库的单文件源码随项目编译。操作系统的权限限制和文件系统隔离用于约束程序可访问的资源。代价是许多能力要自己补齐，包括解析 Cookie、验证表单和查询参数、转义输出；他对自写工具是否合适有保留。作者认为现代内核已降低创建进程的成本，若性能成为问题可转向 FastCGI，但文章没有给出负载测试数据。

原文链接：https://prophitt.me/writing/a-modern-web-app-in-c

论坛讨论链接：https://news.ycombinator.com/item?id=50058528

采集到的两条 HN 评论关注 CGI 能否简化部署。首位评论者指出 BusyBox 内置支持，并用层层容器与直接运行命令的对比说明，简单业务未必需要庞大环境。他强调这并非通用架构，而是把工具做成输入明确、可复现的独立命令，便容易接入网页、测试或隔离环境。另一人分享实际用法：他的 Python 服务既能独立运行，也能作为 CGI 脚本，适配时需处理缺少重写规则的限制。他在老款树莓派上服务约十名固定用户，认为轻量方案适合个人或一次性软件；这一规模不能说明大型网站的表现。

## 6. PS2 游戏静态重编译到浏览器：《GT4》《战神2》已跑通 (Show HN: PS2 games statically recompiled to WebAssembly)



开源项目 PS2 Web Recomp 把 PS2 游戏机主处理器的机器代码预先翻译成 C++，再编译为 WebAssembly，让游戏在浏览器运行。主处理器无需逐条解释执行，其余操作系统和硬件仍由运行时模拟，图像交给 WebGPU 绘制。项目说明展示了两款游戏：《GT4》可从启动进入比赛并保存进度，作者在笔记本集成显卡、Chrome 和两倍原生分辨率下，跑到该 PAL 版本的每秒 50 帧；《战神2》在原生分辨率的激烈战斗中达到每秒 60 帧，两倍分辨率时为 48 至 60 帧。构建脚本读取用户自己的光盘镜像，先分析代码，再试运行以补全静态分析遗漏的函数，并收集向量单元程序进行预编译。优化包括减少显卡任务提交、缓存重复纹理上传，以及将模拟放到独立线程。作者提醒，目前只跑通这两款游戏，其他游戏可能遇到未实现的系统调用或图形功能；项目不含游戏数据，生成的游戏代码应留在用户自己的机器上。

原文链接：https://github.com/snuri00/ps2-web-recomp

论坛讨论链接：https://news.ycombinator.com/item?id=50052251

HN 的主要争论是，快速出现的重编译项目该如何建立信任。有人担心新项目缺少成熟模拟器圈的长期审查；有评论者认为源码可被检查，也有人指出把恶意代码塞进原生程序，比借游戏镜像攻破模拟器更容易。另一方强调此次展示的是 WebAssembly，认为其运行环境能降低恶意软件风险。还有人建议沿用统一模拟器，把审计集中在一个实现上。讨论也延伸到 AI 对编程工作的影响：有人虽不喜欢职业变化，仍欣赏这些新成果，也有人觉得爱好同样受冲击。关于重新运行旧游戏会否削弱大厂投资意愿，评论者意见分歧，并未形成共同结论。

## 7. 把 Wi-Fi 7 路由器改成无线电接收机：每秒采样 3.2 亿次 (Turn a WiFi 7 Router into a 320Msps Software Defined Radio Receiver)




开源项目 W1700K SDR 把 Gemtek W1700K 系列 Wi-Fi 7 路由器改造成宽带软件定义无线电接收机。它使用联发科 MT7996 无线芯片记录原始无线电采样数据，再由路由器主芯片通过万兆以太网传给 Linux 电脑，在浏览器显示频谱、信号随时间变化的瀑布图，并调整频率、增益和滤波器。接收覆盖 2.4、5 和 6 GHz 频段，可选每秒 4000 万至 3.2 亿次的 14 位复数采样。最高速率下，设备把部分数据无损紧凑编码，以适应网络带宽；主机可校正采样处理带来的频谱边缘衰减，每秒生成 100 幅频谱。项目自行编写无线芯片固件，按原厂固件运行轨迹逐寄存器还原初始化和校准，不需要下载厂商固件。安装需要串口适配器和万兆网卡，会替换原有操作系统，并先备份闪存以便恢复。作者明确它只接收、不发射；部分闪存型号尚未在实机验证，访问未公开的寄存器也可能导致设备挂起。

原文链接：https://github.com/h0m3us3r/w1700k-sdr

论坛讨论链接：https://news.ycombinator.com/item?id=50055593

HN 评论围绕“常见无线网卡能否变成廉价无线电实验平台”展开。有人提到同一作者也改造过 ESP32，希望普通笔记本网卡也能开放类似能力。另一方提醒，无线网卡的射频硬件往往围绕特定频段设计，2.4 GHz 虽可覆盖蓝牙和 Zigbee，却不能因此获得任意频率的接收能力。有评论者指出，读取采样数据不等于解锁芯片全部功能，处理能力、传输带宽和帧解析延迟仍会限制用途。另有人认为，约 40 美元的 RTL-SDR 已能提供更有趣的频率范围，购买专用接收器也可能比改装路由器更实用，同时还能继续用原网卡上网。

## 9. 《超级马力欧 64》开发者回忆：靠反复试玩打磨移动与镜头 (The Making Of Super Mario 64 – full Giles Goddard interview (2001))





一份 2001 年对任天堂程序员 Giles Goddard 的访谈，记录了《超级马力欧 64》如何摸索三维游戏的操作方式。Goddard 主要负责开场可拉扯的马力欧脸部，并回忆最终团队大约有 15 人，另有幕后协助者。项目在 N64 硬件出现前就已启动，先借 SGI 工作站上的接口模拟环境开发；最初用键盘控制马力欧，之后用改装的世嘉手柄，再不断尝试 N64 控制器原型。他说，角色动画很早就成形，宫本茂却花了数月反复试验镜头视角和移动方式，重点是玩家操作时的感觉。团队靠大量实际游玩微调细节，也为可玩性舍弃遮挡水下视线的效果。看似宽阔的关卡则利用紧凑、曲折的结构和分区切换，减少同时绘制的场景。文章于 2010 年公开这份较完整的访谈笔记；发布者说明原始提问未保留，现有问题是事后重建，回答也带有回忆的不确定性。

## 10. 橘猫毛色之谜：X 染色体上的一段 DNA 缺失改变色素生成 (Secret of Orange Cats Revealed After 60-Year Search)





两支独立研究团队把橘猫毛色追溯到 X 染色体上的 Arhgap36 基因：其非蛋白编码区域缺失约五千个 DNA 碱基对，改变了基因表达。斯坦福团队发现，橘色毛发对应的皮肤细胞中，该基因的 RNA 表达量约为非橘色猫的十三倍；在包含 188 只猫的数据库中，受检橘猫均携带这段缺失。九州大学团队也锁定同一基因，发现表达增加会抑制部分色素相关基因，使深棕至黑色的真黑素转向红至黄色的褐黑素。雄猫通常只有一条 X 染色体；雌猫有两条，若分别携带橘色与非橘色版本，细胞随机关闭其中一条，就会形成不同颜色的斑块。两条都携带橘色突变的雌猫也可全身橘色，三花猫则还涉及额外的白斑突变。文章强调，目前没有科学证据把这段突变与橘猫的行为或认知联系起来；观察到的表达增加主要在色素细胞中。这篇文章回顾的是 2024 年已公布预印本、2025 年发表于《Current Biology》的研究。
