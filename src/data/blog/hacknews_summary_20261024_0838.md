## 1. Claude为239个测试入口生成有条件的不崩溃证明 (LLMs are making formal software verification feasible at a much larger scale)





Anthropic 与 Theorem 合作，让 Claude 为一百二十三个开源库中的二百三十九个测试入口生成形式化安全证明。方法不是不断尝试更多输入，而是把现有模糊测试转成数学规格：在约束内，任何输入都不能触发崩溃或断言失败。模型写证明，独立的 Rocq 检查器检查它是否满足规格。

实验针对编译后的 RISC-V 指令，限定程序在 Linux 上以单线程、静态二进制运行，内存预算固定，输入小于六十四兆字节。这种做法也帮助模型发现并修补了常规测试难以触及的漏洞，例如只在约二十兆字节特殊输入下出现的解压器越界写入。研究方公开了部分证明与机器形式模型，供他人复核。

关键边界是，证明通过不等于整库没有错误：它只覆盖选定入口及所写规格，内存检测工具也会遗漏某些错误。开发者仍需信任规格、机器模型和检查器，并核查它们是否符合真实部署环境。修改程序后再证明，还需审查补丁未为避免崩溃而破坏原功能。

原文链接：https://www.anthropic.com/research/formal-verification

论坛讨论链接：https://news.ycombinator.com/item?id=50202217

HN 讨论把焦点放在“究竟证明了什么”。一位开发者分享，自己把数据库的 C 实现和 Rust 重写版本都转换成 Lean，再让模型证明两者行为相同；他称已覆盖约百分之十二、相当于七万行原 C 代码，但仅限单线程。有人质疑，把旧实现当规格会继承复杂语义，主张采用更简单、可读的规则；另一人回应，重写时有时正需要连旧错误都保持兼容。更关键的追问是，转换代码的编译器自身是否正确。作者承认尚未验证它，认为当前价值首先在于找到实际差异。这说明发现漏洞有用，与获得完整可信保证，是不同层次的成果。

## 2. Kimi K3.1 Pro发布，完整权重计划11月4日前开放 (Kimi K3.1 Pro and K3.1 Pro Highspeed)





Kimi 发布 K3.1 Pro 及高速版，主打编程、三维创作和长流程任务。它是三万亿级参数模型，支持百万 token 上下文；高速版被官方描述为同等能力下快两至三倍。模型现已接入聊天、办公、编程产品和接口，完整权重计划在十一月四日前发布。

K3.1 Pro 基于前代继续后训练，增加了多领域强化学习的计算投入。厂商报告，终端编程测试 Terminal-Bench 4.0 得分百分之六十五点七，三维重建测试 BenchCAD 在使用工具时为百分之九十二点七；这些是发布方给出的特定测试结果，不是所有任务均领先的证明。

公司还强调事实准确性改进：在自建的高难度事实核查压力测试中，单条事实声明的幻觉率从前代的百分之二十三点四降到八点三。该测试故意选择容易出错的题目，因此八点三不能当作日常回答的总体错误率，也不同于整段回答至少有一处错误的比例。

原文链接：https://www.kimi.ai/blog/kimi-k3-1-pro

论坛讨论链接：https://news.ycombinator.com/item?id=50212065

HN 的主要话题是，模型更愿意反驳用户，是否比一味迎合更好。一位评论者形容 Kimi 会直接指出用户反复追问也不会改变建议，有人觉得这比稍受质疑就改口更可信。反对者提醒，坚持先前说法不代表最初判断有根据，也可能只是重复上下文中的任意结论。另有人认为，明确表达错误观点反而容易定位误解，而迎合式改口可能掩盖同一个问题。讨论又涉及这种风格来自系统提示、训练语料还是后训练奖励。发言多是对 Kimi 的总体印象，并非受控的新版本评测；语气坚定与事实正确仍应分别判断。

## 4. Fable 5.1 图像藏消息：50 条短句的实验 (How does Fable 5.1 hide messages in images?)




Nikita Kezin 等研究者让 Fable 5.1 把指定短句藏进 SVG 图像，再让新会话中的同一模型尝试读回，观察它会自选什么编码，以及没有事先约定规则能否解码。实验包含十五种语言的五十条消息，使用最大推理强度。解码器只收到渲染后的 PNG，没有 SVG 源码，但可调用 Python 和图像分析工具。三十三幅图采用高度编码，例如把一排楼房的高度或星星的位置对应到字母顺序；重音、大小写等信息有时另用屋顶灯、旗帜等提示补上。研究者报告，同模型恢复了三十九条，即百分之七十八；判定会先去掉非字母数字、忽略大小写，再以文本相似度至少九成计作成功，并非要求逐字完全一致。跨模型时，GPT-6 Astra 解出了 Fable 的四十四条消息，反方向恢复四十二条。这个结果来自主动要求藏句的实验，不是发现模型自发秘密通信。作者也指出，解码时的工具调用仍明显可见，因此没有据此声称已出现危险的隐蔽通信。

原文链接：https://www.lesswrong.com/posts/WHEQps5PK8LrrcTAb/how-does-fable-5-1-hide-messages-in-images

论坛讨论链接：https://news.ycombinator.com/item?id=50201445

HN 评论对实验的新意有分歧。有用户认为，按图形高度藏字母过于简单，传统图像隐写可以更细微、信息密度更高；另有人举出把信息放进像素低位的思路。回复者提醒，这篇实验研究的是语言模型直接生成 SVG 文本，再从渲染图中读回，和任意修改位图像素的条件不同。也有人觉得模型常先给出容易理解的玩具方案，需进一步提示才会采用复杂办法；对此，另一支讨论认为，工具框架可以自动反复调整提示，因此效果不只取决于用户最初那句话。这些评论没有否定所报告的解码结果，争论主要在任务设定、技术难度及其意义。

## 5. Alien Sampling寻找研究群体不易想到的合理组合 (The alien space of science: Coherent but cognitively unavailable directions)


一项研究提出Alien Sampling，希望让人工智能寻找科学上说得通、现有研究群体却不容易想到的方向。方法先把一万六千零六十八篇大模型论文拆成概念单元，再聚成可重组的“想法原子”。两个模型分别评价组合是否合理，以及已有作者群体是否具备提出它的研究背景；系统优先挑选合理性高、按发表记录估计较难被想到的组合，最后让语言模型展开为研究提案。这不同于只要求聊天模型随机想些新点子。研究者称，生成的方向比所比较的大模型基线更多样，单条质量在人类盲评和后续实验报告比较中仍有竞争力。在时间验证中，系统只用二〇二五年以前的数据建模，筛取不到百分之一的候选空间，找回后来论文中出现的组合，效果为随机机会的三十五点九倍。这里衡量的是概念组合的回溯命中，并不是发现重大成果的成功率。作者也指出，系统只能重组文献已有概念，发表记录不能覆盖研究者全部知识；小规模评审和有限实验尚不能证明这些提案会长期产出科学突破。

原文链接：https://arxiv.org/abs/2603.01092

论坛讨论链接：https://news.ycombinator.com/item?id=50195002

HN中，一位论文合作者解释，目标是让生成方向避开已有研究群体的熟悉路径，而不是只增加提案数量。他介绍按作者发表史训练可及性模型，也提到将想法送入自动研究流程后，普通模型常回到可解释性主题，所抽样的另类组合则保持了不同方向。他还分享扩大文献规模后的搜索工具。另一位研究隐写与隐蔽通信的读者表示，工具覆盖面令人印象深刻，但查看自己的细分领域后降低了期待：文献里存在大量贡献有限的重复工作，论文密集未必说明方向重要，有时恰恰意味着需要换条路。争论提醒，重组和排名的表现仍需由领域知识与实际研究结果检验。

## 6. 自己写容器运行时，才发现Docker的幕后机关 (Docker is weird)


作者为了学习而动手写容器运行时，发现平时看似独立的容器，在Linux上其实仍是宿主内核运行的进程，只是受到一组隔离和资源限制。命名空间决定进程能看见什么，控制组限制资源用量，网络还需要额外安排；系统并没有一个单独包办全部能力的“容器”开关。镜像则为进程提供根目录所需的文件，运行时准备好这些文件，再改变进程看到的根目录，启动应用。文章接着讨论底层实现为何复杂：runc使用Go，但Go运行时会管理多个线程，而某些隔离相关系统调用需要在单线程条件下完成，因此还要在Go初始化前借助C代码处理；创建目标进程时，也会重新执行自身来组织子进程。作者还注意到，常见Docker守护进程通常具有管理员权限，部分底层接口需要相应特权。无根模式并非不存在，但网络等功能会引入用户态实现的额外复杂性。这是一次尚处早期的学习记录，重点在理解熟悉工具怎样拼接内核能力，而不是发布可替代Docker的新运行时。

原文链接：https://codeandcake.dev/posts/2026-10-22-docker-is-weird

论坛讨论链接：https://news.ycombinator.com/item?id=50202681

HN讨论转向Docker的早期历史，创始人表示自己已多年未参与开发，但愿意回答问题。一位听众回忆，2013年的五分钟演讲是当天最有意思的展示，却没进入他给团队写的会议摘要；一年后，团队已大量使用Docker。他因此追问，产品为何迅速普及。创始人说，原以为只会向十几个人展示尚未完成的项目，到场才发现闪电演讲安排在主舞台；演讲后，大批观众涌向公司展位，营销团队却还准备介绍原来的DotCloud产品。其他在场者也回忆，当时有人觉得它像解决依赖安装的复杂办法，也有人看到潜力，却没预料后来的影响。

## 7. jank：让Clojure直接接入C++原生生态 (Jank – The native Clojure dialect with seamless C++ interop)



jank是一种面向原生程序的Clojure方言，把常见的Java互操作换成与C++直接交互。开发者引入头文件后，就能调用函数、使用模板、处理重载和异常，不必逐个编写类型或函数的注册桥接代码；底层沿用C++类型系统，也能生成C++代码。它保留了交互式开发方式：借助Clang和LLVM的即时编译能力，在编辑器连接的交互环境里输入代码、执行并观察结果，持续修改程序。准备分发时，还可以提前编译，生成较紧凑的二进制产物。项目管理以Leiningen为基础，依赖管理体验受Cargo启发，构建系统可寻找已安装的原生依赖，也可从源码构建。官网分别用读取文件大小、处理文件系统异常，以及调用图形界面和窗口库的示例，说明这种互操作如何用于实际程序。团队也将函数式、不可变数据与原生库结合的方式定位于游戏开发。但成熟度仍有限：作者在HN补充，目前处于不太稳定的alpha阶段，计划在1月提供更稳定的beta。

原文链接：https://jank-lang.org/

论坛讨论链接：https://news.ycombinator.com/item?id=50202762

HN关注交互式原生开发能否让智能体更高效地试验代码。有人认为，交互环境加上不可变数据，可以减少反复重启和完整构建；另一位结合自己的Clojure代码库表示，智能体很善于通过交互执行尝试方案。这些是用户经验，尚不是jank的性能对照测试。讨论随后落到实际困难：模型如今能否可靠闭合括号，编辑时会不会破坏整个项目？几位回复者认为近期模型已有改善，也提到过去可用结构化编辑工具维持语法正确。作者则强调项目已持续开发多年，并非临时让模型生成；他请用户试用并报告每个不顺手之处，体现出目前仍在打磨工具链的阶段。

## 8. OnKey：先听原曲，再对照音高轨迹练唱 (Show HN: OnKey – I'm a bad singer, so I built an app to show where I'm off-key)



OnKey 是免费的开源 Mac 练唱工具，会先听一遍用户播放的歌曲，学习主唱旋律，再把后续演唱的实时音高画在参考音符上，给出分数和逐行报告。歌曲由用户自己的 Spotify、Apple Music 或浏览器中的 YouTube 播放，应用不提供、串流或下载音乐。学习发生在歌曲结束后：模型先分离主唱，再跟踪音高、生成按音节排列的音符条；之后靠音乐声音定位进度。评分允许低八度演唱，也不会因稍微唱迟一点就扣罚。应用要求 M1 或更新的苹果芯片，以及 macOS 14.2 以上，并需麦克风和系统音频权限。项目说明，原曲只在内存中分析，不保存到磁盘，演唱录音和学到的旋律留在本机；但这不等于完全离线，它会为识曲发送短音频指纹，并联网获取歌词、封面和更新；识曲、歌词和更新检查可关闭。若用扬声器跟唱，录音仍可能混入原曲。作者将它定位为在家练习工具，提醒用户不要分享学得的旋律或带原曲的录屏。

原文链接：https://github.com/dsmurrell/onkey

论坛讨论链接：https://news.ycombinator.com/item?id=50195488

HN 评论重点讨论，视觉反馈能否帮助练习，又会不会变成依赖。有用户以节奏学生过度依赖可视节拍器为例，提醒学习者最终仍需认真听自己的声音、辨认错误，别让制作和维护工具挤占练习时间。另一位认为，好的教学软件应随着技能提高逐步撤去辅助，而不是始终追求最省力。作者回应，应用提供迷你模式，可不看音高轨迹演唱，之后再回听并检查表现。也有人觉得无需开发者预先编排曲库很有吸引力，能增加练唱动力；一位做过卡拉 OK 项目的用户则追问音乐获取与授权问题。这些评价并没有证明工具能带来长期教学效果。

## 9. Local Wikipedia：只看步行半小时内的百科条目 (Local Wikipedia: Wikipedia, but only for things a half hour walk from you)


Local Wikipedia把维基百科变成一份附近地点的阅读清单：输入城镇、地区、地标或邮编，也可以让浏览器提供当前位置，再浏览周边带地理坐标的条目。它主打步行约半小时的范围，但并非无论何处都严格按这一尺度筛选。地点太少时，网站会在大约六英里内取最近的二十五处；地点太多时，则只保留最近的五百处。这让乡村与密集城区得到的结果数量和覆盖范围有所不同。页面提供首页、随机条目、字母索引和切换地区等入口，方便从熟悉的地方开始阅读，或偶然发现附近已有百科记录的事物。内容直接来自维基百科，只有已经标注坐标的页面才会进入这一地方版本，因此它展示的是现有条目的空间切片，并非现场调查生成的全新地方志。网站说明，位置留在当前浏览器中，分享链接不会包含该位置；这项说明不能扩展为对所有网络请求的独立隐私审计。它也明确声明，与维基百科官方没有隶属关系。

HN讨论很快从附近有哪些条目，转向哪些地方值得被记录。一位住得偏远的用户说，最近的百科条目要走三个多小时，身边却有许多对自己重要的小地点，并半开玩笑地考虑是否应该补写。另一人提醒，个人亲历未必适合直接进入维基百科。有人推荐另一个地图故事项目，读者却抱怨，页面没有立即展示故事地图，更像尚无内容的介绍站；该项目作者接受反馈，并承认可展示内容不足。另有人分享校园里的安静角落。这些回复关心的是正式百科覆盖与个人地方记忆的差距，针对另一网站的界面批评并非对Local Wikipedia的测试结论。
